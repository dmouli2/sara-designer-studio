@AGENTS.md

## Commands

```bash
npm run dev            # Turbopack dev server (needs SUPABASE_URL, SUPABASE_SERVICE_ROLE_KEY, SESSION_SECRET in .env.local)
npm run build           # production build
npm run start            # serve the production build
npm run lint              # eslint
npm test                   # vitest run (single run, CI mode)
npm run test:watch          # vitest watch mode
npm run test:coverage        # vitest run --coverage (must stay >= 90% lines/statements/branches/functions)
npx vitest run src/lib/dal.test.ts   # single test file
npx vitest run -t "test name"        # single test by name
```

There is no signup flow — the first admin account is seeded manually via `supabase/seed.sql` using a bcrypt hash from `node scripts/hash-password.mjs "<password>"`.

## Architecture

**This is a modified Next.js (16.2.9) with renamed/added APIs — do not assume upstream Next.js behavior.** Before using an unfamiliar API, check `node_modules/next/dist/docs/`. Two deviations already in use in this repo:
- `middleware.ts` is renamed to `proxy.ts` / `export function proxy(...)` (`src/proxy.ts`).
- `next/cache` exports a `refresh()` function (in addition to `revalidatePath`), used alongside `revalidatePath` after mutations that affect client-cached data (see `src/app/actions/orders.ts`).

**Backend is ports-and-adapters, not direct Supabase calls from routes/components.** Dependency rule: only depend downward (domain types → repository ports → adapters), never sideways into a vendor SDK.
- `src/lib/db/types.ts` defines the `Database`/`StaffRepository`/`OrderRepository` port interfaces. `src/lib/db/index.ts` exposes a `getDb()` singleton that wires in the Supabase adapters under `src/lib/db/supabase/`. Same pattern for images: `src/lib/storage/types.ts` (`ImageStorage` port) + `src/lib/storage/index.ts` (`getImageStorage()`) + `src/lib/storage/supabase/imageStorage.ts`.
- `@supabase/supabase-js` may only be imported inside `src/lib/db/supabase/`, `src/lib/storage/supabase/`, and the shared client factory `src/lib/supabase/client.ts` that both adapters use — never from a route, component, or Server Action directly.
- Tests reset these singletons with `resetDbForTests()` / `resetImageStorageForTests()` rather than re-mocking modules.
- `src/lib/mock.ts` no longer holds orders/staff — it's static reference data only (dress types, line-item presets). Real orders/staff live in Supabase Postgres (migrations in `supabase/migrations/`), and so does the fabric price list (`fabrics` table, admin-managed from the new-order wizard via `FabricManagerSheet`).
- Order images are **not** stored as base64 in Postgres (that blew through the DB quota fast). `orders.sketch_data_url`/`reference_image_urls`/`material_image_urls` hold Storage paths; `orderRepository.ts`'s `findById`/`create`/`update` resolve those to fresh signed URLs on every read (full galleries), while `list()` omits sketch/reference entirely but does resolve `mainMaterialImageUrl` — the first material photo only, batch-resolved for the whole page in one Storage call (`getSignedUrls`) instead of per-order, since order cards show that single thumbnail everywhere (list, queues) while full material/reference galleries only render on detail pages.

**Auth has two layers, and only one of them is real.**
- `src/lib/session.ts` signs/verifies a JWT (via `jose`) stored in the httpOnly `sds_session` cookie.
- `src/proxy.ts` only decrypts the cookie for a fast, optimistic redirect — it never hits the database.
- `src/lib/dal.ts` (`verifySession()` / `requireRole(roles)`) does the real authorization: it re-fetches the staff record from `getDb()` on every call and redirects if the account is missing/inactive or lacks the role. Every Server Action must call `requireRole(...)` itself — proxy-level auth is not sufficient.

**Server Actions are the only DB access point for UI code.** `src/app/actions/{auth,orders,staff}.ts` are `"use server"` modules: each exported action calls `requireRole()` first, then `getDb()`. Mutations end with `revalidatePath(...)` (and sometimes `refresh()`) for every route that displays the changed data — see `revalidateOrderPaths()` in `orders.ts` for the pattern.

**Roles and routing:** `Role = "admin" | "master" | "tailor"`. Admin works under `/admin` (orders list/detail/new, staff list/detail/new). Master and tailor each get `/{role}/queue` and `/{role}/orders/[id]`. `roleHome(role)` (duplicated in `src/proxy.ts` and `src/app/actions/auth.ts`) picks the post-login landing route.

**Multi-piece orders** (`orders.pieces`, migration 0012) let one Blouse *or Salwar* order hold several garments cut to the *same* measurements, each with its own delivery date, handed over on its own day. **`pieces` is null for a single-garment order — null means "not split", not "no pieces", and every code path for a null-pieces order is byte-for-byte what it was before the feature existed.** **The count is editable afterwards too** — `OrderEditInput.pieceCount` on the admin edit screen, reconciled server-side by `reconcilePieces()` (never a client-supplied array): a delivered piece can't be removed, ids are never reused (a payment points at one), and shrinking to exactly the delivered count is refused because that would complete the order without collecting its balance — the last garment has to leave through `deliverPiece`. `materialSource` is absent unless the garments genuinely differ (a "same material for all" tick, on by default), so a uniform order stores nothing extra and reads exactly as before; `buildMaterialLabel()` in `src/lib/utils.ts` is the single definition of the one-line `Order.material` summary both the wizard and the edit screen write. **The entry form asks only "how many"** — no name or date per garment, because almost every customer collects the whole order at once; all pieces take the order's delivery date, and a garment that later needs its own is re-dated from the order page (`updatePieceDue`). The wizard's stepper (`canDressHavePieces` in `src/lib/mock.ts`, gated by `FEATURE_MULTI_PIECE`) lives in **step 1 beside the material inputs** — because `OrderPiece.materialSource` lets a customer bring cloth for two garments and buy the third, so the count has to be known before the fabric questions can be asked. It defaults to 1 and only sends `pieces` when the count is ≥2; `buildPieces()` in `src/lib/pieces.ts` mints the ids server-side (`p1`, `p2`, …). `deliverPiece(id, pieceId, collect?)` hands one garment over — **gated only on the order not being cancelled or already fully delivered, never on how far along it is**: this shop doesn't use the master/tailor assignment, so its orders sit at `new` for their whole life, and an early version that required work to have started made the feature unusable (and, because Next.js strips Server Action error messages in production, surfaced as "check your connection" rather than the real reason). an earlier piece may collect any part of the balance (or nothing), the **last** pending piece settles the whole remaining balance exactly like `deliverOrder`. **Every date the admin records works the same way** — a hand-over, a whole-order delivery, and all three alteration steps: it defaults to today, accepts any earlier day (the shop writes things up when it gets a moment, not at the counter) and refuses a future one, enforced by `resolveEventDate()` server-side and `EventDateField`/`isInvalidEventDate` in the UI. `orders.delivered_on` (migration 0013) is where a single-garment order's delivery date lands, since only multi-piece orders have per-garment dates; the last piece leaving sets it too. The **hand-over date is the admin's to choose** (defaults to today, may be backdated, never postdated — the shop records a hand-over when it gets a moment, not at the counter); it dates both `OrderPiece.deliveredAt` and the ledger entry, so the money reads as arriving the day the garment did. `deliveredAt` is a calendar date like every other human-meaningful date here — only `OrderPayment.at` was ever a timestamp, and it now follows the same day. `OrderStatus` gained `partly_delivered` for "some out, some still here" — like `"delivered"`, `updateOrderStatus` **throws** on it, since only `deliverPiece` can know it; the admin's status dropdown renders it as a disabled option so a partly delivered order shows its real state, and the orders list leads with a "Part Delivered" chip (beside Overdue / In Alteration) so orders with garments still on the shelf are findable in one tap. Handing the *whole* order over stays one action — `deliverOrder` marks every remaining piece delivered — so the common case costs nothing extra. Use `isMultiPiece` / `pendingPieces` / `deliveredPieceCount` / `nextDueDate` from `src/lib/utils.ts` rather than touching `order.pieces` — in particular **`nextDueDate(order)`, not `order.due`, is what an order card should show and check for overdue**, because `order.due` is the *last* garment's date and would hide an earlier piece running late.

**Alterations** (`orders.alterations`, migration 0012) track a delivered garment that came back. **An alteration is an episode in a delivered order's life, not a pipeline stage: `order.status` stays `"delivered"` throughout**, so revenue, the delivered count, `computeSummary` and every Reports figure are deliberately untouched by one. What changes is the *display*: `orderDisplayStatus(order)` (in `src/lib/utils.ts`) returns `in_alteration` / `alteration_done` in place of `delivered`, and `StatusBadge`, the admin list's "In Alteration" filter and the customer WhatsApp update all read from it — `STATUS_CONFIG`/`CUSTOMER_STATUS_LABELS` are keyed by `OrderDisplayStatus`, not `OrderStatus`. `openAlteration(order)` (the record with no `redeliveredAt`) is the single definition of "in alteration right now". The admin flow is three actions, each offering only the next step: `startAlteration` (delivered order, none already open) → `completeAlteration` → `redeliverAlteration` (closes the record; it stays listed as history). No charge is captured — alterations are free by shop policy. Gated by `FEATURE_ALTERATIONS`, which hides the entry point but never hides an alteration already open.

**Payment ledger** (`orders.payments`, migration 0012): one entry per post-placement collection, because a multi-piece order can be paid off across several visits. It is an **audit trail layered over the two-entry model, not a replacement** — `finalPayment` remains the running total and `finalPaymentMethod` the latest method, so `orderBalance()` and all Reports arithmetic are unchanged. The advance is deliberately not in the ledger. The detail page only renders the breakdown when there is more than one entry.

**A payment can arrive two ways at once.** `PaymentSplit` (`{cash, upi}`) is the shape money takes at every capture point — the advance in the wizard and the edit screen, the balance at delivery, and a part payment at a piece hand-over. A single-method payment is simply the other side at zero, so nothing downstream branches on "was this split". Storage keeps the existing shape wherever it can: **a split collection writes one ledger entry per method** (same `at` and `pieceId`, so it still reads as the one hand-over it was), which means `OrderPayment` is unchanged and `collectedSplitOf()` just sums the ledger; only the advance needed a column (`orders.advance_split`, migration 0014) because it isn't in the ledger. `advanceMethod`/`finalPaymentMethod` are **null when a payment was split** — no single method describes it — and are the fallback for every order taken before splits existed; read `advanceSplitOf()` / `collectedSplitOf()` from `src/lib/utils.ts` rather than the method fields directly, and `describePaymentSplit()` for the label. `PaymentSplitPicker` is the shared control: Cash / UPI / **Both**, with the two amount boxes only under "Both", so an ordinary payment is still one tap. It lights **nothing** until money is attributed — an empty split is not a choice — and the amounts must add up to what's being collected (enforced in the UI and re-checked server-side).

**Payments** are two entries, not one: `advance`/`advanceMethod` taken at placement (captured in the wizard and editable on the edit screen) and `finalPayment`/`finalPaymentMethod` collected at delivery. `PaymentMethod` is `"cash" | "upi"`. **Always compute what's owed with `orderBalance(order)` from `src/lib/utils.ts`, never inline** — `amount - advance` was the old rule and it left every delivered order showing a balance forever and inflating `pendingBalance`/`balanceDue` in Reports. Delivering goes through the admin-only `deliverOrder(id, method)` action, which computes the balance server-side from the stored order; `updateOrderStatus` **throws** on `"delivered"` so no caller can hand an order over without recording the payment. `DeliverOrderDialog` is the UI. `supabase/migrations/0011_delivery_payment.sql` settled the orders delivered before this existed, leaving their method null (genuinely unknown — the UI renders "method not recorded").

**Sharing with the customer:** the WhatsApp share is available both on the post-placement success modal (`buildOrderWhatsAppMessage` — the full receipt with `ORDER_TERMS`) and, at any point afterwards, from the admin order detail page (`buildOrderStatusWhatsAppMessage` — a short progress update using `CUSTOMER_STATUS_LABELS`, not the workshop status labels; hidden for cancelled orders). Both open a `wa.me` link the admin taps Send on — nothing is sent automatically and no order state changes. The tracking token is deliberately **not** a field on `Order` (it would ride along in every list payload and both role queues); the detail page gets it from `orderRepository.findPublicToken(id)` via the admin-only `getOrderShareToken` action.

**Order editing** is admin-only (`updateOrder` in `src/app/actions/orders.ts`, UI at `/admin/orders/[id]/edit`) and partial: only changed fields ride in the patch (whitelisted — never status/assignments/dress/image columns), and only changed photo galleries ride in the FormData, flagged `sketchChanged`/`referenceChanged`/`materialChanged` = "1". A changed gallery is re-sent in full (kept photos are fetched back from their signed URLs via `galleryEntryToFile` in `src/lib/image.ts`) and rewrites its fixed storage slots: upload slots 1..n first (upload is upsert), then delete leftover higher slots — never delete-then-upload. Delivered/cancelled orders are not editable (enforced in both the action and the page).

**Order domain model** (`src/types/index.ts`): `Order.measurements` is a discriminated union (`GarmentMeasurements` = blouse | salwar | generic) picked by dress type — see the matching form components in `src/components/orders/`. `OrderStatus` is a fixed pipeline: `new → cutting → cutting_done → stitching → hemming_hook → ready → delivered`, plus `partly_delivered` (multi-piece only, written solely by `deliverPiece`) and `cancelled`. Order items are the dress category's `LINE_ITEM_PRESETS` rows plus anything the admin adds: `LineItemsEditor` (shared by the wizard and the edit screen) treats **rows past `presetCount` as custom** — editable name, removable — which is also how a scan's unmatched handwritten rows become fixable. `OrderLineItem.amount` is the **per-piece price** — totals are fabric cost + Σ qty × amount (orders stored before this rule keep their saved `Order.amount` untouched; only their line breakdown renders as qty × price). Measurement field order mirrors the printed slips exactly — notably **UB is printed above Bust** (salwar: above `B`) and is always the smaller number, so the forms, `MeasurementGrid`, the extraction prompt and `emptyBlouse`/`emptySalwar` all keep that order; `ubBustWarning` in `src/lib/extraction/normalize.ts` flags (never auto-corrects) a scan that reads UB > Bust. Measurement fields and line items carry optional free-text remarks (`fieldNotes`/`topNotes`/`pantNotes` maps keyed by field, `OrderLineItem.note`), and salwar `top.oShalwar`/`lShalwar` are optional legacy fields no longer on the entry form (still displayed for old orders). `sketchDataUrl` / `referenceImageUrls` / `materialImageUrls` are storage paths, not raw image data. Photos are sent to `createOrder` as **multipart Files in a separate FormData argument, never as base64 strings inside the action arguments** — React's action deserializer hard-caps string characters inside nested arrays at 1e6 ("Maximum array nesting exceeded"), which real two-photo orders blew through; `next.config.ts` also caps the action body at 4mb (Vercel's own ceiling is 4.5MB), with a matching pre-submit check in `NewOrderWizard`. Server-side, `storeSketch`/`storePhotos` in `src/app/actions/orders.ts` upload the files and persist storage paths. Material photos (fabric close-ups, captured via camera right after choosing material source in the wizard) are required — at least one per order — and the first one is always `mainMaterialImageUrl`, the single thumbnail shown on order cards everywhere; the full `materialImageUrls` gallery only renders at the top of detail pages (admin/master/tailor + the public tracking page).

**Scan-to-draft-order (order slip OCR):** admin photographs a filled order-book spread (`/admin/orders/scan`, entry card on the new-order type screen), a vision model reads it into a `SlipExtraction` (`src/types`), and the result is parked as a **draft** (`draft_orders` table, uuid ids). There is no intermediate review page: a finished scan (and every card on the `/admin/drafts` list) opens `/admin/orders/new?draft={id}` directly — the manual wizard prefilled from the extraction, with collapsible scan-photo/warnings panels on top; discarding a draft lives on its list card. **Drafts never advance the order-id sequences** — the prefilled `NewOrderWizard` (its `scan` prop) and submits through the normal `createOrder`, where the real S…/B… id is reserved; the wizard then calls `confirmDraft(draftId, orderId)` and the scan photo rides along as a reference image. The extractor is a port (`src/lib/extraction/types.ts`, `getSlipExtractor()` singleton) with a Gemini adapter (`src/lib/extraction/gemini/`, plain fetch, `GEMINI_API_KEY`/`GEMINI_MODEL` env, free-tier 429 retry); `src/lib/extraction/normalize.ts` is the pure extraction→wizard-prefill/warnings translator (numbers-only rule: non-numeric pen marks go to measurement comments; line items fuzzy-match `LINE_ITEM_PRESETS`; written Total vs items total mismatches become warnings the admin must resolve). **The advance needs two independent signals before it is prefilled** — a readable number *and* `SlipExtraction.advanceBoxFilled` — because a model that reads the Total or the "Given" box into `advance` invents money the shop never took, and it does so with high confidence; a number without the flag is dropped and surfaced as a warning instead, and any prefilled advance always raises a confirm-against-the-photo warning. `advanceBoxFilled` is optional so drafts scanned before it existed still parse (they fall back to trusting the value). `createDraftFromScan` returns a `CreateDraftResult` (`{ok:true,id}` / `{ok:false,message}`) rather than throwing — Next.js replaces the message of any error thrown out of a Server Action with an opaque digest in production, so a reason the admin needs to read has to travel back as data; `UserFacingError`/`userMessageFor` in `src/lib/errors.ts` decide which messages are safe to show. **`/admin/orders/new` must never `redirect()` for an already-confirmed draft**: `confirmDraft` revalidates, Next re-renders that route as part of the action response, and the redirect would fire while the wizard is still showing its success modal — the page passes `staleDraftOrderId` to `NewOrderWizard`, which navigates only when it isn't holding a freshly placed order. The whole feature is behind the `FEATURE_SCAN_ORDERS` code constant in `src/lib/features.ts` (alongside `FEATURE_MULTI_PIECE` / `FEATURE_ALTERATIONS`, which gate *creating* new ones but never hide data already written) — flipping it off hides the entry, redirects the scan/drafts routes, and makes every action in `src/app/actions/drafts.ts` throw. Empty measurement templates live in `src/lib/measurements.ts` (shared by the forms and the normalizer — don't re-declare them in components).

**Testing setup** (`vitest.setup.ts`) globally mocks `next/navigation`, `next/headers` (`cookies`), `next/cache`, `next/font/google`, and `next/image`. Reuse the exported `mockRouter`, `mockCookieStore`, `mockRevalidatePath`, `mockRefresh` rather than mocking these modules again in individual test files. Some `src/lib` tests (crypto/session code using `jose`) run under a `@vitest-environment node` file-level directive because `jose`'s webapi build breaks under jsdom's vm realm — follow that pattern for other server-only, DOM-free lib code.

**SketchCanvas** (`src/components/orders/SketchCanvas.tsx`) sizes its backing bitmap to the box it is displayed in (via `ResizeObserver`, capped at 1600px on the long side so the PNG stays inside the photo payload budget) rather than using a fixed 800x480 at a locked 5:3 — that locked ratio letterboxed "fullscreen" into a band across the middle of a phone. Pen/eraser widths are CSS pixels scaled by the bitmap's pixel ratio, and a size change redraws the existing sketch contained-and-centred, never stretched.

**PWA:** `public/manifest.json` + `public/sw.js`, served via the route handler at `src/app/sw.js/route.ts`, plus `ServiceWorkerRegister`/`InstallBanner` components. The app is mobile-first — verify UI changes at ~430px width.
